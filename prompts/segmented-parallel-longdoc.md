# 分段并行长文生成 · 判定与执行协议

> 用法：交给具备「并发调用子任务」能力的 agent harness。
> 核心不是提示词模板，而是**第一步的判断**——判断错了，后面全错。

---

## 一、先判断能不能切（唯一判据）

> **把中间某一段删掉，问：后面的段还能写对吗？**

- **能** → 信息并行。**适用本协议。**
- **不能** → 信息串行。**放弃分段，直接一次写完。分段只会更差。**

⚠️ **最容易误判、也最值钱的一类：「看起来串行、实际并行」。**
逐步教程、流程说明、参数清单、分项规则——表面是"第一步、第二步"，但每一步的内容都来自材料，而不来自上一步算出的结果。
**这类任务体量最大，也是这套方法真正值钱的地方。**

反例（禁止分段）：数学证明、逐步推导、连续计算、任何"下一步必须用上一步算出的数"的任务。

---

## 二、为什么有效（一句话）

单个请求输出时，每次只出 1 个 token，却必须把全部模型权重从显存搬运一遍。
**实测：此时显存带宽已用掉 90%，而算力利用率不到 1%。**

切成 N 段并行后，同一次权重搬运产出 N 个 token——**把闲置的算力填上了**。

实测（单卡 GB10 / 27B bf16 / 2048 上下文）：同时跑 64 条序列，总吞吐是单条的 **34 倍**，而每条序列自己的耗时只慢 88%。

---

## 三、执行步骤

1. **串行出大纲**（1 次调用）。此后固定不变，所有段共用。
2. **N 段并行生成**（N 次**并发**调用）。
   - 每段提示词里**只能有**：原始材料 + 大纲（只有标题）+ 本段的要求。
   - **绝对禁止**放入任何其他段的正文——否则你替它做了串行工作。
3. **k 轮融合**（每轮 N 次**并发**调用）。
   - 每轮把**全部 N 段**给每一段看，要求它与其余部分在术语、事实、数字、时间线上保持一致。
   - **用新段替换旧段**；历史留在文件系统里，**不要累积进提示词**。
   - 每轮测量改动量，衰减到阈值以下即停（不要凭"看起来一致了"提前停）。
4. 组装成一份文档。

---

## 四、参数怎么定

| 参数 | 规则 | 实测依据 |
|---|---|---|
| **N**（段数） | 在单步效率跌破 60% 前尽量大 | 效率：16→83%、32→68%、64→**53%**。**推荐 N = 16~32** |
| **k**（融合轮数） | 成本 ×(1+k)，下限 1（至少要一轮互相看见） | k=2 时总成本 3 倍 |

**成本公式：**

```
加速 = N / ((1 + k) × 单步比)
```

---

## 五、三条红线

1. **生成任何一段时，不得让它读到他段正文**（只能给材料 + 大纲）
2. **融合轮用新段替换旧段**，不把历史累积进提示词
3. **输出照原样记录**，不重跑、不修正、不挑好的那次

---

## 六、什么时候不要用

| 情况 | 原因 |
|---|---|
| 任务信息串行（证明、推导、连续计算） | 深度是问题本身，切开必错 |
| N 个交付物之间**不需要一致** | 不必付融合的 k 轮成本 |
| 按 token 计费、且服务商批已填满 | 你付 `(1+k)` 倍的钱换时延，不划算 |
| 自有硬件、单用户长文档 | ✅ **甜点区**：省时延也省机时 |
