## 0. 先读这一段

**你的角色是「执行方」，不是「裁判」。**

这个实验要检验一个假设：「分段并行写 + k 轮融合」能否在更短的时间里达到「一次写完」的质量。

**实验的可信度完全依赖执行方的纪律。** 任何一处自作主张，都会让结果作废。所以本手册里带 **【硬性】** 标记的条目，是绝对不可偏离的。

**你不需要判断结果好坏，也不需要理解这个架构。** 你只需要：**严格按规范跑、如实记录、匿名化提交。**

---

## 1. 硬性约束

### 【硬性】1.1 全程同一模型、同一参数

所有条件（基线 / 分段 / 融合）必须用**同一个模型、同一份量化精度、同一组采样参数**。

采样参数固定为：

```
temperature = 0.7
top_p = 0.9
max_tokens = 固定值（见任务文件）
seed = 每道题固定（同一道题的不同条件用不同 seed，但同一条件重复运行时用同一 seed 组）
```

**跑完一个条件再跑下一个是不允许的——必须把三个条件在同一批次里跑完，避免机器状态漂移。**

### 【硬性】1.2 不得修改提示词

任务文件里给的提示词是**逐字固定**的。不得：

- 增加"请仔细思考"
- 增加"请分步骤"
- 调整标点或语序
- 加入任何 system prompt 里没有的内容

**如果任务文件没写 system prompt，就不要加 system prompt。**

### 【硬性】1.3 不得修改原始材料

材料是逐字固定的。**不得摘要、不得改写、不得补充。**

### 【硬性】1.4 不得"帮忙"

模型输出得不好、跑题、格式不对——**照原样记录，不要重跑、不要修正、不要挑好的那次。**

唯一允许重跑的情况：**请求报错（超时、连接失败、OOM）**。重跑时必须在日志里标明 `retry: true` 及原因。

### 【硬性】1.5 不得输出多余内容

除了任务要求的正文，**不要输出任何前言、后记、"希望对你有帮助"、思考过程说明。**

如果模型自己输出了这些，**照原样保留**，不要删。

## 2. 你需要做的两件事

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **阶段一** | 环境校准：测 batch 耗时曲线 | 不需要任务集，**现在就能做** |
| **阶段二** | 跑实验：三个条件 × 每道题 | 需要任务集 |

**先做阶段一。** 它的结果决定阶段二是否值得跑——如果 batch 并行没有加速，后面全白做。

---

## 3. 阶段一：环境校准

### 3.1 目的

测出这个唯一决定加速比的数字：

> **batch size 从 1 增大时，单个 decode step 的耗时怎么变。**

### 3.2 测量步骤

**【硬性】上下文长度要固定**，且要和你阶段二实际用的长度接近（建议 **2048 token**）。

对 batch ∈ {1, 2, 4, 8, 16}，各做以下操作：

1. **预热**：先用同样的 batch 跑 3 次完整请求，丢弃结果（避免首次调用的编译/分配开销计入）
2. **测量**：用完全相同的输入（同一段填充文本，凑到约 2048 token），让模型生成**固定 256 个 token**
   - 关闭 EOS 提前停止，强制生成满 256
3. **分别记录两个数**：
   - **prefill 耗时**（首 token 出现前的时间）
   - **decode 耗时**（从首 token 到第 256 个 token 的时间）
4. **重复 5 次，取中位数**（不要用平均值）

### 3.3 输出格式

写入 `results/phase1_batch_timing.json`：

```json
{
  "model": "<模型名与量化精度>",
  "gpu": "<显卡型号与显存>",
  "context_tokens": 2048,
  "output_tokens": 256,
  "measurements": [
    {"batch": 1,  "prefill_ms_median": 0, "decode_ms_median": 0, "decode_ms_p90": 0, "tokens_per_sec": 0},
    {"batch": 2,  "prefill_ms_median": 0, "decode_ms_median": 0, "decode_ms_p90": 0, "tokens_per_sec": 0},
    {"batch": 4,  "prefill_ms_median": 0, "decode_ms_median": 0, "decode_ms_p90": 0, "tokens_per_sec": 0},
    {"batch": 8,  "prefill_ms_median": 0, "decode_ms_median": 0, "decode_ms_p90": 0, "tokens_per_sec": 0},
    {"batch": 16, "prefill_ms_median": 0, "decode_ms_median": 0, "decode_ms_p90": 0, "tokens_per_sec": 0}
  ]
}
```

**另一个必须单独测的数：**

> **单步耗时比 = batch=10 时一个 decode step 的耗时 ÷ batch=1 时一个 decode step 的耗时**

这个数直接换算成加速比：

| 单步耗时比 | 预期加速比（N=10, k=2） |
|---|---|
| ≈ 1 | **5×** |
| ≈ 2 | 2.5× |
| ≈ 10 | **无收益** |

**测完先报告这个数，等操作员确认再进阶段二。**

### 3.4 注意事项

- **必须排除模型加载时间**（只计生成阶段）
- **必须排除首次调用预热**
- **同一台机器、同一份驱动**，中途不要重启
- 如果显存不足导致 batch 无法跑满，**如实记录你能跑到的最大 batch**，不要降精度凑

## 4. 阶段二：跑实验

### 4.1 三个条件

对每道题，跑三组：

| 条件 | 做法 | 输出 |
|---|---|---|
| **A0 基线** | 把材料全文给模型，一次写完 | 1 份完整文档 |
| **A1 分段·单轮** | 先出大纲，再按给定的分段方案，每段单独生成 | N 段（拼起来算一份） |
| **A2 分段·多轮** | 在 A1 基础上，做 k = 1…8 轮融合 | 每轮 N 段 |

### 4.2 A0 的提示词

```
以下是原始材料：

<材料全文>

请基于以上材料，写一份完整的文档，共 {N} 个部分：
{各部分标题列表}

要求：直接输出文档正文，不要输出其他内容。
```

### 4.3 A1 的提示词

**第一步：出大纲**

```
以下是原始材料：

<材料全文>

请为一份 {N} 个部分的文档列出大纲。每个部分一行，格式为「部分N：标题」。
只输出大纲，不要输出其他内容。
```

**【硬性】大纲生成后不再修改。** 三个条件共用同一份大纲（A0 也用这份大纲做标题列表）。

**第二步：并行生成 N 段**

对第 i 段：

```
以下是原始材料：

<材料全文>

这是文档的大纲：
<大纲全文>

请只写其中的【部分{i}】，标题为「{标题}」。
直接输出该部分正文，不要重复标题，不要写其他部分。
```

**【硬性】每一段的请求里都只放它自己那部分的要求，不要放其他段的提示。** 这是"并行"的定义——各段互不可见。

### 4.4 A2 的融合提示词（三种变体都要跑）

第 k 轮，对第 i 段：

**变体 V1（保守）**

```
以下是一份文档的全部 {N} 个部分：

<所有段落的完整内容，按顺序>

请修订【部分{i}】，使其与其他部分在术语、事实、数字、时间线上保持一致。

规则：**只做必要的修改。** 不需要改的地方保持原样。
只输出修订后的【部分{i}】正文，不要输出其他内容。
```

**变体 V2（中性）** —— 把规则一行换成：

```
规则：检查是否存在不一致之处，并修正它们。
```

**变体 V3（激进）** —— 换成：

```
规则：仔细审查该部分与其余所有部分的衔接，全面改进一致性。
```

### 4.5 迭代与停止

- 每轮结束后，**用新的 N 段替换旧的**（不是累积到提示词里）
- **连续跑满 8 轮**，不要提前停止

**【硬性】不要因为"看起来已经一致了"就停止。** 提前停止会丢掉要测的曲线。

### 4.6 时间记录

**每一轮、每一段、每一次调用，都要记录：**

```json
{
  "task_id": "A-01",
  "condition": "A2",
  "variant": "V1",
  "round": 3,
  "segment": 4,
  "prefill_ms": 0,
  "decode_ms": 0,
  "output_tokens": 0,
  "wall_clock_ms": 0,
  "retry": false,
  "timestamp": "ISO8601"
}
```

**A0 的总耗时**和 **A2 每轮的总耗时**（该轮内 N 段并行，取最慢那段的时间）要单独汇总。

### 4.7 重复次数

**每道题、每个条件，独立跑 3 次**（不同 seed）。

**【硬性】不要只跑 1 次。** 单次结果的随机性可能大于你要测的效应。

## 5. 提交格式

### 【硬性】5.1 匿名化

**交给裁判的文件里，绝对不允许出现能识别条件的信息。**

- 文件名：`pair-{task_id}-{序号}.md`
- 内容格式：

```markdown
# 原始材料

<材料全文>

---

# 版本一

<正文>

---

# 版本二

<正文>
```

- **禁止**出现"A0"、"基线"、"分段"、"A1"、"A2"、"轮次"等字样
- **禁止**出现小标题注明来源

### 【硬性】5.2 顺序随机

哪一份放"版本一"、哪一份放"版本二"，**由你用随机数决定，并把映射关系写进一个单独的、不提交给裁判的文件** `results/mapping.json`。

**裁判不会问，你也不要说。**

### 5.3 一次一对

**不要一次提交 20 对。** 一对一对提交。

### 5.4 时间数据单独提交

时间数据**不匿名化**，单独放在 `results/timing/` 下，因为裁判判质量时不看它。

## 7. 遇到问题怎么处理

| 情况 | 怎么做 |
|---|---|
| 显存不足，batch 跑不到 10 | **如实记录能跑到的最大 batch**，不要降精度。继续用那个 batch 跑实验，并在报告里标注 |
| 模型输出被截断 | 记录为截断，**不要重跑**。同时记录截断时的 token 数 |
| 模型拒绝回答 | 照原样记录 |
| 输出格式完全不对（比如只回了"好的"） | **照原样记录，不要重跑** |
| 请求超时 | 重跑，标 `retry: true` |
| 同一道题某一段反复失败 | 停下来，报告操作员。**不要自己换提示词** |
